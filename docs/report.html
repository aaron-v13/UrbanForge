1. Executive Summary

UrbanForge has progressed from an initial frontend prototype into a comprehensive, production-ready full-stack web application. The platform integrates high-performance client-side 3D WebGL rendering (using Three.js) with a robust, modular Model-View-Controller (MVC) Express.js backend. User authentication and real-time 3D city layouts are persistently synchronized with MongoDB Atlas via Mongoose ODM, paired with a resilient local JSON fallback engine to ensure absolute system reliability.

  • Complete Client Experience: Interactive 3D scene featuring 12 customized GLTF models, gizmo transformation handles (Move, Rotate, Scale), real-time urban vitals panel (Happiness, Population, Pollution, Water, Energy, Budget), and fully responsive navigation/authentication interfaces.
  • Full-Stack Data Synchronization: Seamless bidirectional communication connecting user authentication, cryptographic session cookies, and immediate database write/delete operations for placed city buildings.
  • Dual Database Engine: Primary cloud integration with MongoDB Atlas powered by Mongoose Schemas (User, Building, CityLayout) alongside an automatic JSON file fallback system (data/users.json, data/buildings.json).
  • Template Engine Implementation: Dynamic server-side diagnostics view powered by EJS at /status, fulfilling the academic evaluation criteria for template engine integration alongside static file serving.

5. 3D Simulator & Real-Time Database Synchronization

A primary technical accomplishment of UrbanForge is the immediate synchronization between user interactions in the 3D WebGL viewport and the backend database:

  • Instant Placement Persistence: When a building is placed on the 100×100 coordinate grid, the client generates a unique entity ID (bld_<timestamp>_<hash>) and dispatches a POST /api/city/buildings payload containing coordinates (X, Y, Z), rotation, model path, and scale factor. Mongoose inserts/upserts the record in MongoDB Atlas.
  • Instant Deletion Sync: Selecting any placed object and clicking Delete (or pressing Del) immediately executes an HTTP DELETE /api/city/buildings/:buildingId, removing the document from the database in real time.
  • World State Rehydration: Upon browser reload or revisiting the site, loadSavedBuildings() automatically fetches existing records from MongoDB and re-instantiates all 3D meshes at their exact coordinates.

6. Backend Engineering & Schema Design

The backend is strictly architected using MVC design principles within the backend/ folder: 

backend/
├── config/db.js              # MongoDB Mongoose connection & status inspector
├── controllers/
│   ├── authController.js     # User registration, login verification, session audit
│   └── cityController.js     # Real-time CRUD handlers for 3D buildings & cities
├── models/
│   ├── Building.js           # Mongoose ODM Schema for 3D world entities
│   ├── CityLayout.js         # Mongoose ODM Schema for city world saves
│   └── User.js               # Mongoose ODM Schema for user accounts
├── routes/
│   ├── authRoutes.js         # Authentication REST API routes
│   └── cityRoutes.js         # Building & layout REST API routes
├── services/fileStorage.js   # Reliable JSON fallback storage engine
├── views/status.ejs          # EJS dynamic server-side template
└── server.js                 # Central Express configuration, middleware, static files

Database Schemas (Mongoose ODM)

  • User Schema (models/User.js): Stores name (String), email (String, unique, indexed, lowercase), password (String, salted bcrypt hash), and automatic createdAt / updatedAt timestamps.
  • Building Schema (models/Building.js): Stores userId (String, indexed), buildingId (String, unique), assetId & assetName (String), modelPath (String), scale (Number), position ({ x, y, z }), and rotation ({ x, y, z }).
